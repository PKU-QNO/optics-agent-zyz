# doc-sync — 设计文档同步系统（面向用户）

## 定位

- **doc-sync = 面向用户**——用户查看的主交互渠道（设计现状 + 待决策 + 决策历史）
- **transition-wrapup = agent 自看**——恢复压缩上下文（互补，不重叠）
- 用户说「**创建一个 doc-sync 文档系统**」即建立全套
- **⚠️ 背景**：doc-sync 是 P5 skill 生态调研课题的**落地产物之一**——P5 调研了多个候选 skill（ABCD 四类范围），doc-sync 只是其中**提前完成的一个**，其余仍在调研/待落地（如 verification-before-claim 等）

## 适用范围

- **大项目**（多线并行、设计复杂、agent 迭代频繁）→ 完整主副文档系统
- **小项目** → 一份主文档就够了（单文件概览，无需拆副文档）

## 结构

```
<工作区>/memory/<XX>-sync/       # XX 根据工作区实际内容命名（如 self-evo-main → sem-sync、optics_agent → optics-sync），不要所有工作区都叫 sem-sync
├── PROJECT-SYNC-<date>.md      # 主文档：多线设计总览（概览）
├── 00-待决策清单.md             # 唯一 human 入口（编号 00 排最前）
├── 01-<主题>.md                 # 副文档：详细 flow 设计
├── 02-<主题>.md
└── ...
```

## 必含：方向 × 阶段总览表（项目全景）

主文档必须有「每个方向/项目 × 阶段状态」总览表——用户一眼看全貌（谁在调研/计划/实现/已实现/已推迟）：

```md
| 方向/项目 | 阶段 | 说明 | 详档 |
|-----------|------|------|------|
| <方向 1> | 🔵 调研 / 📋 计划 / 🟡 实现 / ✅ 已实现 / ⏸ 已推迟 | <一句话> | [NN-主题](NN-主题.md) |
```

**阶段图例**：🔵 调研 → 📋 计划 → 🟡 实现 → ✅ 已实现 / ⏸ 已推迟
（图例固定，全项目统一）

**⚠️ 状态粒度（关键）**：`✅ 已实现` ≠ 已接入生产。阶段与接入程度是两维：

| 状态 | 含义 |
|------|------|
| 🔵 调研 | 只调研，未动手 |
| 📋 计划 | 方案定了，未实现 |
| 🟡 实现中 | 代码/系统在写 |
| ✅ 原型完成 | 可运行原型，**未接入主系统**（如 markdown_library.py 未投入 memento 搜索）|
| ✅ 已接入 | 已接入主系统（如 fast hook 已装 / P0a 已落地）|
| ✅ 生产 | 生产发布（gate 全过）|
| ⏸ 已推迟 | 暂缓 / 搁置 |

> 表格状态列必须区分"原型完成未接入"vs"已接入"——**打 ✅ 前先问：它接入主系统了吗？** 原型完成 ≠ 已实现

**主文档末尾附简表**：除 §0.5 总览外，主文档末尾（§8 待决策后）附一张**任务/状态/备注简表**（同 §0.5 的紧凑版），方便快速扫一眼所有任务现状：

```md
## 附录：任务状态简表

| 任务 | 状态 | 备注 |
|------|------|------|
| <任务 1> | ✅/🟡/🔵/⏸ | <一句话备注> |
| <任务 2> | 🟡 | <一句话备注> |
```


## 核心设计原则（借鉴 grill-with-docs）

### 1. 主文档 = 概览（不是正文）

- **多用 ASCII 图表示各种 flow**（记忆流 / hooks 触发 / 文件流 / API 接入 / 任务生命周期）
- 状态表 + 跳转链接（相对路径，同目录）
- 头部注明"**唯一 human 入口 = 00-待决策清单**"
- 末尾 §8 = 待决策概要 + **单跳转**（不连环跳转）
- 用户只看主文档就能知道"现在项目在干什么 + 有哪些待决策"

### 2. 00-待决策清单 = 设计树 frontier（grilling 借鉴）

> **这是你唯一需要拍板的地方**。用设计树思想：每个决策分支展开，frontier = 可立即回答的问题。

- **每项待决策详细阐述**：
  1. **前因后果**（背景 / 轮次 / 证据 / 为什么现在需要决定）
  2. **待决策内容**（选项表，每个选项的代价）
  3. **推荐选项**（含理由，像 grilling 的 `➡️ 推荐答案`）
- 可引用/重复其他副文档内容（避免连环跳转）
- 末尾附「已决策历史表」（ADR 风格：记录*已决定*和*为什么*，单段可记录）

### 3. 文档内容（主次分明，详略得当）

**主文档**（概览，详略得当——按任务实际主次）：
1. **整个 flow 现状** — 多图 + 状态表（核心，主）
2. **工作历史** — 时间线 / 轮次 / 决策演进（简）
3. **未来目标计划** — 目标 + 计划 + 里程碑（简）
4. **风险清单** — 已知风险 + 对策（简）
5. **已验证 vs 未验证** — 实测确证 vs 猜测（简，result_class 口径）
6. **关键凭据/链接索引** — 重要文件/凭证/外部链接（简）
7. **环境/约束** — 平台 / 工具 / 红线（简）

> 主文档只放各内容概要 + 单跳转；**详细版下沉副文档**（副文档可详细）。

### 4. 副文档 = 详细 flow 设计

- 每个设计 flow 的**详细设计**（schema / 数据流 / 组件表 / 演进轮次 / 风险详情 / 已验证 vs 未验证明细）
- 首尾保留返回主文档链接（`[⬆ 返回主文档](PROJECT-SYNC-<date>.md)`）
- 状态一律 result_class 口径（不夸大完成度）
- **超大 docs 系统**：允许二级副文档（`NN-主题/` 子目录，如 `NN-主题/MM-子主题.md`），一级副文档 = 目录 + 跳转，二级 = 详细

## 同步触发（强制）

1. **每次有新 agent 完成**（codex / 内置子 agent / 任何任务产物验收）→ 同步更新主文档相关节 + 副文档状态表 + 风险清单
2. **用户提出新想法/新决策** → 主文档加节或更新现有节 + 新建副文档（如需）+ 风险清单更新
3. 每次更新后记录到工作日志（可追溯）

## 链接规范（重要）

- 文档内引用**用链接或绝对路径 `C:\...`**，**不用相对路径**（用户可能无法解析）
- 主/副文档之间用相对路径（同目录 `NN-xx.md`）
- 引用 `cases/.../report.md` 等外部证据时给**绝对路径**（含盘符 `C:\`）
