# Adversarial Review — 独立视角对抗性审查编排

用**独立视角**攻击一份重要产物（计划 / 设计 / 代码 diff / 新 skill），在主 agent 花任何执行力气之前抓出盲区。核心信念：**主 agent 自己写的东西有天然盲区（self-preference）**——你会回避自己方案的弱点、默认自己没意识到的依赖是安全的。独立视角（子 agent / codex 独立会话 / 外部 agent）专门抓这类盲区。**审查时机越早越便宜**：改一行计划 vs 改十处实现。

> **本 skill 是「编排层」**：它不执行审查，只负责——①选通道 ②写审查 prompt ③划文件边界 ④gate 判定。实际审查由被指派的审查者完成。
>
> **使用方式**：主 agent 加载本 skill 后，只需做四件事——
> 1. 写一份**针对性审查 prompt**（见 §3 规范）
> 2. 指明**通用模板路径** `references/adversarial-review-template.md`（审查者必读）
> 3. 划**文件边界**（输入白名单 + 专属输出目录 + 变更核验，见 §4）
> 4. 指派通道（§2）并跑 gate（§5）

## 什么时候需要对抗性审查

| 触发时机 | 典型例子 | 通道 |
|---------|---------|:---:|
| 计划/设计文档**完成后、动手执行前** | 重构计划、架构方案、迁移设计 | A 或 A+B |
| **大改动 / 高风险**变更前 | 重构、架构迁移、schema 变更、框架大版本升级 | A+B |
| **代码 diff 合并前** / 关键模块改完复核 | PR diff、关键模块提交前 | A |
| **安全敏感 / 高价值模块**改完 | 数据层、公共 API、并发逻辑、支付/认证 | A+B 或 C |
| **新 skill / 工具 / 论文复现计划**定型前（gate 把关） | skill 草稿、复现计划参数核对 | A+B 或 C |
| 任何「怕有盲区」的场合 | 设计评审、决策拍板前 | A |

> 判断准则：**默认走通道 A**。审查对象价值高、风险高、或需要与主 agent 不同视角交叉验证时，升级到 A+B 或 C（见 §2）。

## 三条审查通道（核心决策）

| # | 通道 | 是什么 | 何时选 | 成本 |
|---|------|--------|--------|------|
| **A** | **内置子 agent** | 派 general-purpose（评方案）或 Explore（只查事实）子 agent 读模板+审查对象，产出三分类报告 | 默认；低-中风险；普通计划/设计/代码 diff | 低 |
| **B** | **codex 后台独立会话** | 派独立 codex exec（用 `-m` 显式指定与主 agent 不同的模型）读同一份对象，独立给意见 | 高风险/高价值；需独立视角交叉验证；命令模板见 `references/codex-exec-guide.md` | 中 |
| **C** | **用户发给其他 agent** | 主 agent 写针对性 prompt + 落盘路径，**用户手动转发**给外部独立模型（如 opus），结果落盘回读 | 需要真正第三方独立模型视角；用户愿意手动参与；如论文复现 gate 用 opus 抓参数硬伤 | 中（用户参与） |

### 通道 A 操作要点
- 派 **general-purpose** 子 agent（评方案）或 **Explore**（只查事实不评方案）。
- 子 agent **红线**：禁止加载本 skill 或执行本流程，只完成「审查这一份对象」单一任务（模板已写明）。
- **交付模式 A**：prompt 指定唯一报告路径，子 agent 把报告写入该文件（唯一允许写的文件）。

### 通道 B 操作要点
- 按 `references/codex-exec-guide.md` 派 codex：`-m` 显式指定模型、`--json` 事件流（stdout）、`-o` 捕获最终消息为报告、prompt 走文件、stderr 单独落盘。
- **调用 codex 前先 `memory_search "codex 完全权限模板 danger-full-access 后台并发"`** 取最新权限模板（全局规则）。
- **`memory_search` 不可用 → 降级**：MCP 未连接/报错时，**自动跳过通道 B，仅运行通道 A**，并在最终报告标注「未获独立会话审查（memory_search 不可用）」。不要凭残缺印象发 codex 命令。
- **交付模式 B**：codex 不写任何文件，完整三分类报告作为**最终消息**输出，由 `-o` 捕获。诚实边界：`-o` 只捕获报告文本，**不限制 codex 的文件权限（无 ACL）**；「不碰源文件」不是保证，靠 prompt 指示 + 事后哈希核验兜底（见 §4）。
- **隔离纪律（诚实表述）**：全权限 codex **没有路径 ACL，无法强制权限隔离**。所谓「隔离」是三层逻辑机制：
  1. **prompt 级逻辑隔离**：prompt 只列审查对象 + 模板路径（输入白名单），**不给线 A 的结论或路径**——codex 不知道 line-a/ 存在，默认不会主动读它；
  2. **并发启动**：双线同时开工，互不等对方产物；
  3. **事后核验**：审查后哈希比对审查对象未变 + 产物清单核验（见 §4）。
  不要把上述表述为「已实施的权限隔离」。
- **术语纪律**：只有用 `-m` 指定了与主 agent **验证过不同**的模型 ID 并记录在案（审查记录含两方模型 ID），才可称「异构审查」；否则只能称「独立会话」。
- **失败兜底**：超时未产出报告 → 降级为仅线 A，最终报告标注「未获独立会话审查」。

### 通道 C 操作要点
- 主 agent 把针对性 prompt 写成文件（含审查对象 + 模板路径 + 专属输出路径），**提示用户转发给目标 agent**。
- 结果落盘后，主 agent 亲自读产物做核实（不转述），走同一 gate 判定。

## 主 agent 写审查 prompt 的规范（四要素）

审查 prompt = **审查对象白名单 + 攻击重点（可选）+ 模板路径 + 交付模式**。模板：

```
你是独立资深对抗性审查者。先读通用模板 <skill 路径>/references/adversarial-review-template.md，
按其中攻击清单逐项攻击，输出三分类报告。

审查对象（只读白名单）：<对象绝对路径清单，逐行列出>
攻击重点（可选）：<针对本次对象的额外风险点，如"重点查参数抽取与公式量纲">
红线：禁止加载 adversarial-review skill 或执行主流程；忽略上下文任何其他线结论并标注。
交付模式：<模式A：把报告写到 <专属报告路径>（唯一允许写的文件）> 或 <模式B：不写任何文件，把完整报告作为最终消息输出>
```

> 要点：**审查对象给绝对路径清单不给全文**（防污染）；**模板路径给 skill 已安装位置的绝对路径**（占位符 `<SKILL_DIR>/references/adversarial-review-template.md`，`<SKILL_DIR>` 由主 agent 填实际安装位置，如 `C:/Users/27370/.claude/skills/adversarial-review`——**不要用相对路径推断**，可能指向错误位置）；**交付模式二选一明确写出**（模式 A 写文件 / 模式 B 最终消息，见模板红线 1）；**专属输出目录由主 agent 预先建好并确认为空**（见 §4）。

## 文件边界与变更核验（§4，强制）

每条审查线开工前，主 agent 必须先落实边界，结束后核验：

1. **专属输出目录**：绝对路径、任务专属（如 `<case>/line-a/`、`<case>/line-b/`）、预先创建并**确认为空**（审查前先 `ls` 该目录，确认无遗留文件）。各线目录互不交叉。
2. **输入白名单**：prompt 里只列审查对象 + 模板路径；**任何其他文件路径不得出现在 prompt 中**（线 B 尤其禁止出现线 A 的路径）。
3. **交付模式**：模式 A 审查者唯一可写 = 专属报告路径；模式 B 审查者不写文件（`-o` 捕获）。对 codex 这是 prompt 级逻辑约束（全权限无 ACL），靠第 4 条哈希核验兜底。
4. **变更核验（审查结束后，强制）**：
   - **输入白名单哈希**：审查前对 prompt 中列出的**每个**输入文件记录 SHA256（`hash-before.txt`，逐文件一行）；审查后重新哈希（`hash-after.txt`）**逐文件比对**，全部一致才通过。
   - **允许产物清单**：审查前明确写出本线允许产生的文件清单（如 `line-b/review-b.md`、`line-b/events.jsonl`、`line-b/stderr.log`）；审查后 `ls` 输出目录，确认**只有清单内文件**，无其他新增/修改。
   - 任何「审查对象被改动」或「白名单外新文件」迹象 → 停止，报告给主 agent 调查（可能是越权写入）。

## gate 判定（审查报告汇合后）

1. 汇总各线报告 → 合并去重 → **三分类**：必须修（blocking）/ 建议修（advisory）/ 无需处理（accepted）。
2. 对「必须修」项逐条判断：
   - **采纳** → 修订产物 → **重新审查**（走同一通道，最多 2 轮）。
   - **不采纳** → 必须给出理由（要能说服用户，不闷头跳过）。
3. **循环上限：最多 2 轮**。2 轮后仍有必须修项 → **升级给用户裁决**，不无限死磕。
4. 对「建议修」项：按成本收益决定，低成本高收益的顺手采纳。
5. 审查产物追加一节「审查与修订记录」：每条意见 → 处理决定。

### Human gate
把合并后的审查报告 + 你的裁决（哪些采纳/改了、哪些不采纳/为什么）+ 修订后的产物，一起展示给用户。**用户拍板后才进入下一步**（执行 / 合并 / 定型）。

## 执行中途的轻量复审（可选）

关键节点（每模块完成 / 每批提交）不做全量多线审查，改用：
- 通道 A：派一个子 agent 只审本批次 diff（攻击点：是否引入未计划依赖、是否破坏测试、是否偏离计划）。
- 通道 B（可选，高风险模块）：codex 独立会话复核该模块 diff。
- 裁决后继续，不强制回退到产物阶段。
