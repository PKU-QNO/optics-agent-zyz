# 对抗性审查实战手册（mie-f 真实经验，供 skill 编写参考）

> 用途：用户要写"发对抗性审查的 skill"。本文档记录主 agent 在本项目（mie-f 数值复现，8 次审查）中实际如何发审查——三种渠道、prompt 结构、目标现状交代法、常见坑。真实案例全部可在 `opus-prompts/` 对照。
> 生成：2026-08-08

---

## 1. 三种发审渠道（何时用哪个）

| 渠道 | 执行者 | 适用场景 | 调用方式 | 产物 | 费用/特点 |
|------|--------|---------|---------|------|----------|
| **A. 内置子 agent**（Agent 工具） | Claude 子 agent | 代码审查、单点核实、文件级核对 | `Agent` spawn，读 `sub-agent` skill，8 字段报告落 `sub-report/` | `sub-report/<task>.md` | 快、便宜；但同模型（self-preference 风险） |
| **B. Codex 后台** | Codex（异构模型） | 完整对抗审查 + 实现 + 验收闭环 | `codex exec` 后台 bash，prompt 落盘 `opus-prompts/`，stdin 喂入，产物落盘 | `notes/*.md` + `data/*.json` | 异构防 self-preference；能干活不只是审；慢（分钟~小时级） |
| **C. 用户手动发强模型** | claude-opus / GPT | 高能力对抗审查（物理/参数/公式/方法学） | 主 agent 落盘 prompt → 用户复制到独立对话 | 结论贴回对话 + 主 agent 落盘 triage | 最强审查力；依赖用户手动；结论回来要 triage |

**路由经验**：
- 常规文件/代码审查 → A（内置子 agent，快）
- gate 前的 spec/参数/公式对抗审查 → C（opus，强模型看物理）
- 数值实现 + 自洽验收 + 审查一体 → B（Codex 异构闭环）
- 拿不准的物理判断、blocker 根因 → C 优先（第 1 轮表2 大 x blocker 就是 C 求解的）

## 2. 通用 prompt 结构（6 段模板）

```
# Opus/Codex 审查任务单 #NN：<任务名>

> 提交给：claude-opus / GPT / codex（对抗性审稿）
> 发起方：mie-f 复现主 agent
> 工作区：<绝对路径>（同一工作区，可直接 Read）
> 时机：<gate 前 / 执行前 / blocker>

## 0. 你的角色
你是**对抗性审稿人**。任务：<一句话目标>。任何参数错都会直接毁掉复现。请逐字核对，不要客气。

## 1. 审查对象
（明确列出待审文件路径，编号）

## 2. 真相源（逐字核对用）
（权威源：原论文 PDF / 讲义 / 教材 / 数据文件——审查者必须能自己打开核对，不能只信待审文件）

## 3. 审查维度
### A. <最高优先维度>（参数正确性/公式/物理）
### B. <次要维度>
### C. <方法学维度>
（每维度下给具体问题清单，编号）

## 4. 输出格式
## 发现的问题（按严重度）
### 🔴 严重（必改）
### 🟡 中等（补）
### 🟢 轻微
## 结论
1. <能否用于实现？是/否+原因>
2. <哪些必须改>

## 5. 纪律
- 逐字对照真相源，不只信待审文件
- 每条问题给"为什么导致错误"的机制
- 核实无误写"✅ 已核实"
- 不要客气
```

## 3. 快速交代目标现状（现状浓缩法）

审查者没有我们的上下文，prompt 开头 3-5 行必须让它瞬间进入状态。格式：

```
## 背景（现状浓缩）
- <这是什么任务>：复现 Alaee 2018 Fig.2（多极分解，表2 vs Mie）
- <已完成>：第 1 轮 Fig.1 gate①②③④ 全过（三曲线自洽 <1%，报告 21 页）
- <本轮进度>：formalization reviewed-ready + 数值验收闭环（Codex）；gate② 待审
- <与上轮差异>：本轮新增金球复 ε 色散（3 源核对）、双面板、表2 vs Mie（无表1）
- <验收标准>：论文原文 "indistinguishable" → <1% + p95<0.1% + abs<2e-3
```

**要点**：
- 只给审查者需要的**决策上下文**，不给过程流水账
- 上一轮已 gate 确认的结论明确说"不重复核"（节省审查火力）
- 本轮与上轮差异**显式列出**（审查者不知道我们的历史）

- 每个 **human gate 前**必有一份对抗审查 prompt（用户拍板流程）

- **执行前**发方法学审查（值不值得做、口径对不对）

## 5. 常见问题（实战踩坑 8 条）

1. **不给真相源** → 审查者只能猜/信待审文件 → 失去对抗意义。必须给"能自己打开核对"的权威源路径。
2. **prompt 太宽泛**（"审一下这个 spec"）→ 审查者自由发挥，漏掉关键点。必须**维度化**（A/B/C + 每维度具体问题）。
3. **审查结论可能错**（即使 opus）→ 教训 8/9：opus 判 Fig.1 y 轴 linear 是对的，但主 agent 当时亲看权威图判 log 也错了——**审查结论必须独立核实**（vision-mcp 多通道），不能盲信任何一方。Codex 审查同理（fig2 验收数字主 agent 逐位重核）。
4. **转述漂移** → 审查结论回传后，主 agent 落盘 `XX-review-triaged.md`（如 `01-review-triaged.md`），triage 每条 R/Y/G 的处理；复述纪律：汇报数字重开原文件。
5. **审查范围与时机不匹配** → 参数审查必须在 gate①（实现前），公式审查在 gate③（编码前）；晚了就返工。
6. **审查 prompt 塞进对话** → 应该落盘 `opus-prompts/` 给路径（用户复制发强模型；codex 走 stdin 喂文件）。对话里只给路径 + 一句摘要。
7. **同模型审查自己**（self-preference）→ 内置子 agent 审自己的代码有盲区；关键 gate 必须异构（opus/gpt/codex）。
8. **期望审查者"干活"** → 对抗审查只判"对不对/值不值得"，不负责实现。Codex 渠道例外（能干活），opus 渠道别指望它写代码。

## 6. 审查结论回来后的处理（triage 流程）

```
1. 主 agent 独立核实：审查者声称的关键数字/方向 → 重开原文件核对（复述纪律）
2. 落盘 triage：逐条列 R/Y/G → 接受/拒绝 + 理由 + 怎么修
3. 修复 → 重新提交审查（如 gate② 硬伤1/2 修复后重新核对）
4. 修复后主 agent 亲验（跑测试/重算数字）
5. gate 裁决：用户看审查结论 + 修复证据
```

## 7. 给 skill 的要点提炼

- **发审时机**：每个 human gate 前 + blocker 时 + 执行前（方法学）
- **渠道选择**：A 内置子 agent（快）/ B Codex 后台（闭环干活）/ C 用户手动强模型（最高能力）
- **prompt 6 段**：角色 / 审查对象 / 真相源 / 维度 / 输出格式 / 纪律
- **现状浓缩 5 行**：任务 / 已完成 / 本轮进度 / 差异 / 验收标准
- **铁律**：审查结论必须独立核实（不信任何一方自述）；落盘不塞对话；异构防 self-preference
